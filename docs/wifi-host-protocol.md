# 汇海体测 WiFi 主机通讯协议

> 本文档根据 `HH.TiYu.Device` 项目源码整理，描述采集器与汇海 WiFi 测试主机之间的 UDP 通讯协议，
> 覆盖当前源码保留的 WiFi 功能：设备发现、采集成绩、下载学生、清空学生、校时（设置时间）、通讯质量检测、参数读写、关机。
> 供长期开发维护参考。修改协议相关代码时请同步更新本文档。
> 本文记录当前客户端实现；涉及固件是否固化名单等行为，仍需设备协议或真机验证。已知实现限制见 §10。

**证据范围**：发送字段来自组包代码；接收字段来自解析器；UI 展示和保存行为另行注明。未取得固件源码、厂家完整协议或真机抓包，本文件不是所有固件版本的兼容性认证。未读取字段不推定为保留值或固定值；“旧版 / 新版”仅指源码按长度选择的两种格式，不对应已确认的固件版本号。本文所有偏移从 0 起，长度单位均为字节。

## 1. 总体架构

| 项 | 说明 |
| --- | --- |
| 传输层 | UDP |
| 业务端口 | 客户端默认目标端口 **10000**（三个 `CreateInstance` 均传入该值）；实例的 `Port` 可修改，源码不能证明固件固定监听该端口 |
| 发现端口 | UDP **48899**，使用 `www.usr.cn` 探测字符串，可广播或单播 |
| 字节序 | 帧中的多字节整数为**大端（Big-Endian）**（源码中 `SEBinaryConverter.ShortToBytes(...).Reverse()`）；ASCII 学号的十六进制还原采用小端，见 §5.5 |
| 校验 | **CRC16-CCITT**：多项式 `0x1021`，初值 `0xFFFF`，无反射、无异或输出（`Crc16Ccitt`） |
| 编码 | 名单下发的学号 / 卡号使用 ASCII，姓名 / 班级使用 GB2312；成绩上报的学号按 ASCII 字符筛选、姓名按 GB2312 解码。学号范围命令和文本成绩使用 `Encoding.Default`，日期 / 旧格式科目使用 BCD 算法 |
| 并发限制 | 事后采集（`HostWifiReader`）与学生下载（`StudentDownloader`）各自最多 **4 台同时工作**，超出排队等待；实时采集不受此队列限制 |

业务通道使用 IPv4 UDP Socket，连接目标 IP / Port 后收发；没有显式绑定本地地址或本地端口，三个类的 `LocalIP` 仅保存而未传入 Socket。发现阶段的广播 Socket 则显式绑定当前本地 IPv4 地址和端口 0。`HHSocket` 每次接收缓冲为 1024 字节，不能把一个超过 1024 字节的 UDP 数据报视为会自动拆成多次完整回调；对端应将较大的协议帧拆为不超过此接收容量的数据报。

核心类分布（命名空间 `HH.TiYu.Device.Wifi`）：

| 文件 | 职责 |
| --- | --- |
| `Discovery/WifiSearcher.cs` | 搜索局域网内的 WiFi 主机 |
| `Control/WifiHost.cs` | 命令通道：校时、关机、Echo、参数读写、采集/下载预处理 |
| `Control/CmdResponse.cs` | 命令应答帧解析 |
| `Control/GetParameterResponse.cs` + `Control/HostParameters.cs` | 主机参数的编解码（TLV） |
| `Collection/HostWifiReader.cs` | 成绩采集：轮询数据请求、接收头帧/数据帧 |
| `Collection/DataResponse.cs` / `HeadResponse.cs` | 成绩数据帧、头帧解析 |
| `StudentDownload/StudentDownloader.cs` | 下载 / 清空学生名单 |
| `Protocol/ResponseBase.cs` / `Crc16Ccitt.cs` | 帧基类（CRC 校验）与 CRC 算法 |

## 2. 通用帧结构

协议使用以下 7 种帧头。`16 02 02` 同时用于成绩数据帧和学生下载应答，需结合当前通道区分，二者长度字段宽度不同：

| 帧头（Hex） | 方向 | 用途 | 长度字段 |
| --- | --- | --- | --- |
| `16 16 01 01` | PC → 主机 | 命令帧（校时、关机、Echo、预处理、参数读写等） | 2 字节大端 |
| `16 01 01` | 主机 → PC | 命令应答帧 | 2 字节大端 |
| `16 0A 0A` | 主机 → PC | 参数应答帧（0x0A 读参数时的响应） | 2 字节大端 |
| `16 16 02 02` | PC → 主机 | 成绩数据请求帧 | **1 字节** |
| `16 03 03` | 主机 → PC | 成绩数据头帧 | 1 字节 |
| `16 02 02` | 主机 → PC | 成绩数据帧 | 1 字节 |
| `16 02 02` | 主机 → PC | 学生下载应答帧 | **2 字节大端** |
| `16 16 0A 0A` | PC → 主机 | 学生下载 / 清空命令帧 | 2 字节大端 |

各帧的 `Len` 都包含长度字段自身及末尾 CRC，不包含帧头。CRC 覆盖 Len 至 CRC 前。常用长度如下（`D` 为命令数据区长度，`N` 为名单人数）：

| 帧 | Len | 完整帧长 |
| --- | --- | --- |
| 普通命令 | `10 + D` | `14 + D` |
| 成绩请求 | 14（0x0E） | 18 |
| 18 字节头帧 | 15（0x0F） | 18 |
| 24 字节头帧布局 | 21（0x15） | 24 |
| 62 / 64 字节成绩帧 | 59 / 61（0x3B / 0x3D） | 62 / 64 |
| 正式 / 测试名单命令 | `13 + 72 × N` | `17 + 72 × N` |
| 下载结束 / 清空命令 | 9 | 13 |

命令应答至少需容纳偏移 11 的状态和末尾 CRC，完整布局至少 14 字节；带偏移 12 主机号的应答至少 15 字节。学生下载应答至少 13 字节。以上是字段互不重叠的布局要求，当前解析器并未完整执行这些最小长度检查。

### 2.1 命令帧（PC → 主机，`16 16 01 01`）

`WifiHost.SendCommand` 组装：

```
16 16 01 01 | Len(2,BE) | SerNo(2,BE) | HostID | Cmd | Sub1 | Sub2 | Data... | CRC16(2,BE)
```

- `Len` = 从 Len 字段自身到 CRC 末尾的总字节数（`list.Count + 4`，即 Len(2) + 载荷 + CRC(2)）。
- `SerNo`：`WifiHost` 的静态 `ushort` 流水号，首次生成 0，之后递增，65535 后回绕为 0；同一命令重发复用同一流水号。当前递增未加锁，并行实例不能保证流水号唯一。
- `HostID`：目标主机号（1 字节）。
- `Cmd / Sub1 / Sub2`：命令字与两级子命令。
- 当前公开方法除采集预处理设置 Sub1 外，Sub1 / Sub2 均发送 0；采集预处理的 Sub2 也为 0。
- CRC16 计算范围：从 Len 字段到 Data 末尾（不含 4 字节帧头，不含 CRC 自身）。

### 2.2 命令应答帧（主机 → PC，`16 01 01`）

由 `CmdResponse` 解析，关键偏移（相对于 `16 01 01` 起始）：

| 偏移 | 字段 |
| --- | --- |
| 3-4 | Len（大端） |
| 5-6 | SerNo（大端，与命令帧对应） |
| 7 | HostID |
| 8 | CMD（回显命令字） |
| 9-10 | 当前 `CmdResponse` 未读取，语义未确认 |
| 11 | **CMDState** 命令执行状态 |
| 末 2 字节 | CRC16 |

`CMDState` 取值（`WifiHost.Socket_OnDataArrivedEvent`）：

| 值 | 含义 |
| --- | --- |
| `0xB3` (179) | 命令执行成功 / 数据就绪 |
| `0xE0` (224)、`0xE1` (225)、`0xE2` (226) | 客户端作为终止等待的状态，多数布尔命令返回 false；三个值各自的固件含义未确认 |

应答帧 CRC 校验范围见 `ResponseBase.IsValid`：从偏移 3 到 CRC 前。

### 2.3 发送与重试机制（`WifiHost.SendCommand`）

- 默认最多尝试 `int.MaxValue` 次，实际近似持续重发；每次发送后等待应答 `interval` 毫秒（默认 1000），没有短时的整条命令总超时。
- 当前实现从接收缓冲中提取到命令应答或参数应答包后，先置位 `_HostResponed`，发送线程即可能停止重发；此时尚未验证 CRC 或匹配 `_CurCmd`，也未核对 SerNo、HostID。
- 之后等待 `_DataEnd` 信号直到 `timeout`（默认 1000 ms）：命令应答须 CRC 合法、CMD 匹配且状态为 0xB3 / 0xE0~0xE2；参数应答分支直接置位，CRC 校验在 `ExtraData()` 中进行。
- 个别命令覆盖默认值：`GotoMainForm` 最多发送 5 次 / 每次等待 100 ms，随后等结束信号 100 ms；`GetHostID` 最多发送 5 次 / 每次等待 200 ms；`SetParameters(blocked:false)` 最多发送 10 次 / 每次等待 100 ms。
- `SetParameters(blocked:false)` 仍是同步调用，只是限制发送次数；参数名不表示异步或立即返回。命令应答 CRC 不合法或 CMD 不匹配时，接收循环没有推进 `_ReceivePacket`，存在持锁空转风险，见 §10。

## 3. 设备发现（`WifiSearcher`）

当前 `WifiSearcher` 实现的发现流程：

1. PC 遍历 `NetTool.GetLocalIPS()` 返回的本机 IPv4 地址，逐个绑定后向 `255.255.255.255:48899` 广播 ASCII 字符串 `www.usr.cn`，不附加 NUL 或换行；另有单播到指定 IP 的重载。地址列表来自本机主机名的 DNS 查询结果，不保证覆盖所有网卡地址。
2. 模块应答按 ASCII 解码，解析器要求恰好 4 段逗号分隔：第 1 段为 IP，第 2、4 段未使用，第 3 段按下划线拆分为至少 3 段（如 `H1_P6_SN123`，也接受更多段）：
   - 第 1 段提取数字 → **主机号 HostID**
   - 第 2 段提取数字 → **物理编号 PhysicalID**
   - 最后一段 → **序列号 SerialNumber**
3. 广播搜索逐个处理本机 IP，每个 IP 默认等待 5000 ms 后收集应答，按 SerialNumber 去重；多网卡时总耗时可能超过 5000 ms。单播搜索默认最多等待约 5000 ms，收到应答可提前返回，其结果不设置 LocalIP。

解析结果存于 `WifiHostInfo`（IP、HostID、PhysicalID、SerialNumber、LocalIP）。

HostID / PhysicalID 按 `byte.TryParse` 解析，失败时为 0；IP 和序列号没有进一步格式或非空校验。结构不满足条件时忽略该应答。这里描述的是当前解析器接受的格式，不意味着所有 USR 模块都使用这四段格式。

## 4. 命令一览（`WifiHost`）

| Cmd (Hex/Dec) | 方法 | 说明 | 数据区 |
| --- | --- | --- | --- |
| `0x0A` (10) | `GetParameters` / `SetParameters` | 读 / 写主机参数 | 写时为 TLV 参数块，见 §9 |
| `0x0B` (11) | `GetHostID` | 读取主机号 | 应答帧偏移 12（从 0 起）为主机号 |
| `0xA1` (161) | `Shutdown` | 主机关机 | 无 |
| `0xA3` (163) | `PreGetNewRecords` 等 | 采集预处理（选数），子命令见 §5.1 | 依子命令 |
| `0xA4` (164) | `PreDownloadStudent` | 下载学生预处理（通知主机进入下载模式） | 无 |
| `0xA5` (165) | `SyncTime` | 校时，见 §7 | 7 字节时间 |
| `0xA6` (166) | `Echo` | 通讯质量检测，见 §8 | 200 字节 0x00~0xC7 |
| `0xAF` (175) | `GotoMainForm` | 命令主机退回主界面 | 无 |

成功判据分两类：

- 多数方法以「应答 `CMDState == 0xB3`」为成功（`PreGetXxx`、`PreDownloadStudent`、`SyncTime`、`Shutdown`、`Echo`、`SetParameters`）。
- 例外：`GetHostID` 只检查接收包非空且长度至少 13，再从偏移 12 取值；该方法自身不检查包类型、CRC、CMD 或状态，也未保证该偏移不落入 CRC。`GetParameters` 只解析参数应答（无此包或 CRC 不合法时返回 null，畸形 TLV 可能抛异常）。`GotoMainForm` 只要最后状态不是 0xE0~0xE2 就返回 true，完全未收到应答时状态仍为初始值 0，也会返回 true，不能据此证明主机已退回主界面。

## 5. 采集成绩

成绩采集由 `HostWifiReader` 实现，分**事后采集**（IsRealTime = false）和**实时采集**（IsRealTime = true）两种模式。

### 5.1 采集预处理（事后采集，Cmd `0xA3`）

开始采集前先通过 `WifiHost` 发送预处理命令，告诉主机要上传哪些记录。`Sub1` 子命令：

| Sub1 | 方法 | 采集范围 | 数据区 |
| --- | --- | --- | --- |
| `0x51` (81) | `PreGetNewRecords` | 客户端称为“新记录”；固件如何维护“已采集”标记未确认 | 无 |
| `0x52` (82) | `PreGetAllRecords` | 全部记录 | 无 |
| `0x53` (83) | `PreGetRecords(beginSid, endSid)` | 学号范围 | 40 字节：起始学号 20 字节 + 结束学号 20 字节，空格（0x20）填充 |
| `0x54` (84) | `PreGetRecords(begin, end)` | 时间范围 | 按当前文化的 `ToString("yyMMddHHmm")` 格式化，再用 `Encoding.Default` 编码；通常为 20 字节数字文本，两端各 10 字节 |
| `0x55` (85) | `PreGetRecords(beginSer, endSer)` | 记录序号范围 | 4 字节：起始 SN(2,BE) + 结束 SN(2,BE) |

UI 层对应 `HostWifiReaderPara.CollectType`：0=全部、1=新增、2=学号、3=时间、4=序号。

学号范围用 `Encoding.Default`，分别从数据区偏移 0 / 20 开始复制、右侧补空格；代码未限制每个标识的编码字节数，超长输入可能跨字段或抛异常。序号范围方法参数为 C# `short`，发送其 16 位位模式。范围是否含端点、空边界含义以及“新记录”标记何时更新，均需固件确认。`RecordCollectTask` 不检查预处理方法的布尔返回值，返回 false 后仍进入轮询。

### 5.2 数据请求帧（PC → 主机，`16 16 02 02`）

`HostWifiReader.SendCommand` 发送以下轮询帧。采集线程每轮先休眠 1000 ms，再发送并等待响应 / 本批数据结束，并非固定每秒发送一次（见 §5.6）：

```
16 16 02 02 | Len(1) | HostID | Flag | 00 | 00 00 | 00 00 | LastSN(2,BE) | 00 00 | CRC16(2,BE)
```

- `Len`：1 字节，= 从 Len 自身到 CRC 末尾的字节数（`list.Count + 3`，固定为 14）。
- `Flag`：事后采集 = `0x11`；实时采集 = `0x00`。
- `LastSN`：当前采集会话中最后通过帧 CRC、HostID 和适用序号检查的记录序号，初始为 0，`Close()` 后重置；数值成绩无效并不会阻止该序号更新。请求字段始终只有 2 字节；接收新版 4 字节序号后仍通过 `(short)_LastSN` 发送其低 16 位，超过 65535 的续传行为需真机验证。
- CRC16 计算范围：从 Len 到 CRC 前。

### 5.3 头帧（主机 → PC，`16 03 03`）

主机收到请求后先回一个头帧（`HeadResponse`），宣告本次传输规模：

| 偏移（18 字节旧版） | 字段 |
| --- | --- |
| 3 | Len |
| 4 | HostID |
| 5-8 | DataBytes（4,BE，本次数据总字节数；为 0 时仅事后模式标记整个采集完成） |
| 9-10 | MaxSN（2,BE） |
| 11-12 | 当前解析器未读取，语义未确认 |
| 13-14 | LastSN（2,BE，本次最后一条记录序号） |
| 15 | 值为 `0x07` 时解析为 EOF=true；当前采集流程不使用该标志判断完成 |
| 16-17 | CRC16（2,BE） |

新版头帧的 MaxSN 在 9-12、LastSN 在 17-20，均为 4 字节大端序号；EOF 在 21，是 1 字节标志。加上末尾 2 字节 CRC，完整结构至少为 24 字节。当前解析按帧总长度 18 / 其它选择分支，未严格校验新版长度；EOF 被解析保存，但采集流程未使用它判定完成。

24 字节布局中偏移 13-16 未读取，CRC 在 22-23；不要根据字段位置猜测未读取区的含义。DataBytes 和 4 字节序号均读入有符号 `int`，最高位为 1 时得到负值；2 字节序号读入 `int` 后为 0～65535。`MaxSN` 被传给接收事件用于进度，代码未通过它验证记录总数；DataBytes 除零值判断外也未用于核对累计数据长度。

### 5.4 数据帧（主机 → PC，`16 02 02`，每条 62 / 64 字节）

`DataResponse` 解析：

| 偏移 | 字段 |
| --- | --- |
| 3 | Len |
| 4 | HostID |
| 5 | 当前解析器未读取，语义未确认 |
| 6-7 | SN（2,BE，旧版 62 字节帧）；新版 64 字节帧为 6-9（4,BE） |
| 8（旧）/ 10（新） | 52 字节成绩记录体 |
| 末 2 字节 | CRC16 |

**序号连续性校验**：仅在 `_LastSN != 0` 且未设置 `UnSerialable` 时，要求收到的 `SN == _LastSN + 1`；首条记录不要求 SN 为 1。不连续时清空当前头帧并置位 `_DataEnd`，结束本批接收；该分支没有直接写异常日志。

收到 `SN == 头帧.LastSN` 只结束当前批次，随后继续轮询。整个事后采集须在收到 `DataBytes == 0` 的头帧后，才标记完成并由采集线程触发 `ReadCompleted`；实时模式不会按此条件自动完成。

### 5.5 成绩记录体（52 字节，GB2312 / BCD 混合）

| 偏移 | 长度 | 字段 | 编码 |
| --- | --- | --- | --- |
| 0 | 20 | 学号 | ASCII；解析器从尾部扫描保留 `[0-9A-Za-z]`、跳过空格，已收集字符后遇到其它非空格字符则停止，结果转大写；8 位且含 A-F、各字符均能按十六进制解析时，将依次解析的 4 字节按小端还原为数字（`RevertNumber`） |
| 20 | 1 | 测试项目代码 | 旧版 BCD，新版原始字节 |
| 21 | 5 | 成绩 | 见下表 |
| 26 | 5 | 记录时间 | BCD：yy MM dd HH mm（年 = 2000 + yy，无秒） |
| 31 | 1 | 性别 + 学号来源 | ASCII `'0'`=女 / `'1'`=男，来源均为 Unknown；否则按 `byte & 0xF0` 取来源，低 4 位 0=女、1=男、其它=“无” |
| 32 | 20 | 姓名 | GB2312 解码后调用 `Trim()`；会去除两端空白，但不会去除 NUL 填充 |

**成绩字段（5 字节）的解析规则**：

| 首字节 | 含义 |
| --- | --- |
| `0xE0` | 后 4 字节为大端有符号 Int32（二进制补码）。项目 6（立定跳远）或 81（纵跳摸高）→ ÷10；项目 15（掷实心球）、16（丢沙包）、100 → ÷1000；其它 → 原值 |
| `0xE1` | 后 4 字节为大端有符号 Int32，统一 ÷1000；此分支不再应用 0xE0 的项目换算 |
| `0xA0` / `0xA1` / `0xA2` | 特殊成绩：犯规（Foul）/ 弃权（Abandoned）/ 未完成（Incomplete）。`GetData()` 保存 SpecialResult，忽略后 4 字节，Result 保持默认 0；该 0 不是有效数值成绩（见 `StudentScoreConverter`） |
| 其它 | 全部 5 字节用 `Encoding.Default` 解码，再按当前文化调用 `decimal.TryParse`，未固定小数点文化；项目 6 且结果 < 10 时 ×100，该判断没有非负下限 |

数值成绩解析失败时标记 `PhysicalRecord.Invalid = true`；特殊成绩单独保存标志。记录时间解析失败则回退为 `2000-01-01`，不会因此设置 `Invalid`。

学号还原示例：`ABCD1234` → 字节 `AB CD 12 34` → 小端整数 `873647531`。这是当前 `SEBinaryConverter.BytesToLong` 的行为，不等同于将字符串作为大端十六进制数解析。

`BCDConverter.BCDtoInt` 实际计算 `(b >> 4) × 10 + (b & 0x0F)`，不验证半字节是否超过 9。合法单字节 BCD 只能表示 0～99；不能据此认定 62 字节格式能按标准 BCD 表达附录中所有大于 99 的科目。日期还会通过 `DateTime` 构造校验，但非标准 BCD 字节仍可能换算成合法日期。

**IDSource（学号来源，掩码后的值，不右移）**：0x00 未知、0x40 (64) 按键输入、0x50 (80) IC 卡物理卡号、0x60 (96) IC 卡学号、0x80 (128) 扫描枪、0x90 (144) 身份证；其它高四位值回退为 Unknown。枚举另定义 `HostStoredData = 10`（十进制），但 `byte & 0xF0` 不可能产生 10，因此当前 WiFi 解析器不会返回这个来源。

**测试项目代码及单位**：解析器保留科目代码，不校验其是否存在于本地字典；附录 A 仅列当前种子字典。`PhysicalItem.ConvertPhysicalItem` 根据匹配到的本地学生性别，将男生的 800 米代码 10 改为 1000 米代码 11、女生的 11 改为 10；无本地学生或其它性别时不改。`DataResponse` 本身不换科目，`StudentScoreConverter` 保存的 TestID 也是原始代码。

附录单位不能直接等同于帧内原始成绩单位。采集 UI 的 `GetScoreFrom` / `ShowRecord` 对字典单位为“分.秒”的科目，将解析后的 Result 按秒调用 `ConvertToMinuteSecond`，例如 150 秒 → 数值 2.30（2 分 30 秒）；该函数先向下取整秒，并使用 `TimeSpan.Minutes` 分钟分量，不能表示任意小时数。立定跳远通常解析为厘米，当 UI 字典单位为“米”时再除以 100。原始成绩保存与 UI 显示转换是不同步骤，不能按附录单位再次对所有原始值统一缩放。

### 5.6 采集时序与容错

```
PC                          主机
 |---- 0xA3 预处理 ----------->|   （仅事后采集）
 |---- 16 16 02 02 (LastSN) -->|   每轮先休眠 1 s，再发送并等待
 |<---- 16 03 03 头帧 ---------|
 |<---- 16 02 02 数据帧 × N ---|
 |      （按连续性规则接收，直到本批 LastSN）
 |---- 下一轮请求 ------------>|   继续轮询；事后模式收到 DataBytes=0 才完成
```

- 发送后最多等待 `_HostResponed` 300 ms；若收到信号，再等待 `_DataEnd`，上限为事后采集 600 s、实时采集 5 s（`RecordCollectTask`）。300 ms 超时只跳过本轮的数据结束等待，接收回调仍可能处理迟到数据；下一轮发送前会清空缓冲和当前头帧。
- `CheckStateTask` 每 5 s 检查一次最后活跃时间：事后模式达到 15 s、实时模式达到 60 s 未进入接收回调则判定掉线（State=1），清空当前头帧并置位 `_DataEnd`，可能提前结束上述数据等待；后续轮询在 State=1 时重建 Socket。活跃时间在校验报文前更新，收到无效数据也会刷新，State=0 不代表成绩有效或业务成功。
- 非实时模式的 `Close()` 会发送 `GotoMainForm (0xAF)` 请求主机退回主界面；触发 `ReadCompleted` 本身不发送该命令，实时模式关闭也不发送。
- `ReadCompleted` / `PhysicalRecordReceived` / `StateChanged` 事件向 UI 层通知进度与状态。

## 6. 下载学生 / 清空学生（`StudentDownloader`）

使用独立的命令通道，帧头 `16 16 0A 0A`，长度、流水号与 CRC 的编码方式与普通命令帧一致，但这里只含一个 Sub 字段：

```
16 16 0A 0A | Len(2,BE) | SerNo(2,BE) | HostID | Cmd | Sub | ... | CRC16(2,BE)
```

| Cmd | 方法 | 说明 |
| --- | --- | --- |
| `0x00` | `DownloadStudents` | 下载正式学生名单（分组发送） |
| `0x80` (128) | `DownloadTestStudents` | 下载测试用学生名单 |
| `0x11` (17) | `CompleteDownload`（`Close()` 时自动发送） | 下载结束通知；固件持久化行为需真机确认 |
| `0xEE` (238) | `ClearStudents` | **清空主机内全部学生** |

下载前应先用 `WifiHost.PreDownloadStudent (0xA4)` 让主机进入下载模式（UI 层流程）。

主机管理 UI 对“下发学生”和“清空学生”都先调用该预处理，但不检查其布尔返回值；随后调用 `StudentDownloader.Open()` 进入工作 / 等待队列。只有 `_IsWorking` 为 true 时才实际发包，因此不能省略 `Open()`。

### 6.1 下载学生数据区

```
学生数(1) | 记录长(1, 固定 72=0x48) | 固定字节 01 | 固定字节 00 | 学生记录 × N
```

**单条学生记录 72 字节**：

上述两个固定字节的固件语义未由源码确认，不把它们定义为版本号或保留字段。完整帧中学生数在偏移 11，记录长在 12，两个固定字节在 13-14，首条学生记录从 15 开始。

| 偏移 | 长度 | 字段 | 编码 |
| --- | --- | --- | --- |
| 0 | 20 | 学号 StudentID | ASCII，右补 0x00 |
| 20 | 20 | 姓名 Name | GB2312，右补 0x00 |
| 40 | 1 | 性别 | `0x31`('1') 男 / `0x30`('0') 女 |
| 41 | 1 | 年级 | 当前固定 0（保留协议字段位） |
| 42 | 20 | 班级 ClassName | GB2312，右补 0x00 |
| 62 | 10 | 卡号 CardID | ASCII，右补 0x00 |

所有字符串按编码后的字节数截取到字段宽度，可能截断 GB2312 双字节字符；空值填零。只有 Sex 为“男”或字符串“1”才写 0x31，其余值均写 0x30。当前 `FrmHosts.UploadStudents` 未赋值 CardID，故该入口实际发送的卡号字段全为 0；表中卡号编码能力供直接调用协议层时使用。

人数直接强转为 byte，协议层不校验上限；调用方应保证 `1 ≤ N ≤ 255`，256 人会写成人数 0，却仍附带 256 条记录。null / 空数组不生成有效 data，不能据此发送“零人名单”。

### 6.2 下载应答（主机 → PC，`16 02 02` 帧）

`StudentDownloadPacket` 解析（偏移从 0 起）：Len(3-4，2 字节大端)、SerNo(5-6)、HostID(7)、Command(8)、Sub(9)、**CommandRet(10)**，末尾 2 字节为 CRC。注意：虽与成绩数据帧同用 `16 02 02` 帧头，这里的 Len 是 2 字节。

`CommandRet` 即 `StudentDownloadResult` 枚举：

| 值 | 含义 |
| --- | --- |
| `0x00` (0) | 接收成功 ReceiveSucceeded |
| `0x11` (17) | 接收失败 ReceiveFailed（收到该码不视为有效应答，继续重发） |
| `0x22` (34) | 存储成功 StorageSucceeded |
| `0x33` (51) | 存储失败 StorageFailed |
| `0x44` (68) | 存储器已满 StorageFull（UI 层收到后中止下载） |
| `0x55` (85) | 清除成功 ClearSucceeded |
| `0x66` (102) | 清除失败 ClearFailed |

### 6.3 发送策略

- 每个下载分组持续重发（次数上限 `int.MaxValue`），每次发送后等待应答 200 ms；清空命令等待 1000 ms。CRC 合法、SerNo / Sub 一致且 CommandRet ≠ 0x11 时停止重发；此处不匹配 HostID / Command，停止重发也不代表存储或清除成功，应结合返回码判断。
- `CompleteDownload` 最多发送 10 次，每次发送后等待应答 100 ms；`Close()` 不检查其是否成功。
- 单个协议帧超过 1024 字节时拆成多个 UDP 数据报发送，每个数据报至多 1024 字节，发送后休眠 20 ms（`SendData`）。拆分后的数据报是同一帧的片段，不各自附加帧头和 CRC。
- 主机管理 UI 按 `maxStudentPertime` 分组，参数控件范围为 1～100，文本初值是 **100 人/组**。字段声明虽初始化为 20，但点击确定时会被控件值覆盖。100 人的完整帧为 7217 字节，分为 7 个 1024 字节数据报及最后 49 字节。
- UI 逐组调用 `DownloadStudents`，只对 `StorageFull` 显式中止；`StorageFailed` 等其它返回码未被当作失败处理。`ClearStudents()` 返回 void，丢弃应答结果，清空 UI 也不核对 `ClearSucceeded`。因此 UI 进度完成不能证明设备存储 / 清除成功。
- 下载及清空流程都在 `finally` 中调用 `Close()`，其中调用 `CompleteDownload (0x11)`；并非只有正常下载结束才执行。排队实例尚未进入工作状态时，结束命令可能只等待而未发出。
- 注意：下载参数对话框中的「先清空」选项（`clearFirst`）在当前 UI 流程中**读取后未使用**（历史遗留，见 `HH.TiYu.UI/README.md`）；要清空需走独立的「清空学生」菜单。
- 应答匹配以 SerNo + Sub 为准；`SerNo` 为实例级递增流水号。

## 8. 通讯质量检测（Cmd `0xA6`，`WifiHost.Echo`）

- 发送 200 字节递增数据（`0x00, 0x01, …, 0xC7`），使用 `SendEchoCommand`：只发一次，固定等待 1000 ms。
- 仅以 `_LastCommandState == 0xB3` 记为一次成功；该状态来自 CRC 合法且 CMD 匹配的命令应答。当前未比较回显载荷是否与发送的 200 字节相同，也未核对 SerNo / HostID，因此成功率不代表载荷逐字节校验通过。
- UI（`FrmHosts` 通讯质量检测）持续循环 Echo，按最近最多 **10 次**的滑动窗口计算成功率；不足 10 次时用实际次数作分母：

| 成功率 | 评价 | 颜色 |
| --- | --- | --- |
| ≥ 0.8 | 通讯质量良好 | 蓝 |
| ≥ 0.6 | 通讯质量一般 | 黑 |
| ≥ 0.5 | 通讯质量较差 | 橙 |
| < 0.5 | 通讯质量很差 | 红 |

## 9. 主机参数读写（Cmd `0x0A`）

- **读**：发送 0x0A 无数据；主机回 `16 0A 0A` 参数应答帧（`GetParameterResponse`）。
- **写**：发送 0x0A + TLV 参数块；成功判据 `CMDState == 0xB3`。

参数应答的 TLV 从整帧偏移 12（从 0 起）开始，至末尾 2 字节 CRC 之前；`ExtraData()` 先验证 CRC，再解析参数区。

参数区为 TLV 序列：`块长(1，含长度字节自身) | 参数ID(1) | 数据(块长−2)`：

| 参数 ID | 写入块长 | 数据字段顺序（未注明长度的均为 1 字节） |
| --- | --- | --- |
| 1 | 5 | 按键学号：最大长度、递增间隔、人工确认 |
| 2 | 4 | 输入设备：扫描枪/身份证、IC 卡物理号 |
| 3 | 5 | 测试结果：确认方式、写入 IC 卡、LED 屏显示 |
| 4 | 4 | 辅助设备：无线音箱、红外防抢跑器 |
| 5 | 6 | 测试限制：测试次数、总时间（2,BE）、进行方式 |
| 129 (0x81) | 3 | 引体向上：难度系数 |
| 130 (0x82) | 9 | 地毯式中长跑：跑道长度(2,BE)、男生距离(2,BE)、女生距离(2,BE)、测试模式 |
| 131 (0x83) | 4 | 标签式中长跑：圈数、测试模式 |
| 132 (0x84) | 3 | 仰卧起坐：躺平模式 |
| 133 (0x85) | 3 | 短跑系列：项目选择 |

`GetBytes()` 固定按表中顺序发送全部 10 块，共 46 字节，写参数完整命令帧为 60 字节；没有“只写已赋值属性”的逻辑，未赋值属性也以 0 发出。读取 ID=1 时兼容块长 4（缺少人工确认字段，补 0）。其它缺失参数保留默认 0，未知 ID 的块被跳过，重复 ID 由后出现的值覆盖；未知块不会在再次写入时保留。

两字节数值在模型中使用 int，发送时转为 short 后取 16 位位模式，未校验范围；调用方需限制在字段可表达的 0～65535 内。读取 TLV 仅以剩余长度 >2 控制循环，没有完整的块长 / 字段边界校验，畸形块可能抛异常；CRC 合法不代表 TLV 结构合法。

> 开关与模式字段保留原始 byte 值，具体取值含义以设备固件协议为准。

## 10. 开发维护注意事项

1. **CRC 范围与帧头长度**：发送与接收均从 Len 字段算到 CRC 前；发送帧跳过 4 字节帧头，应答帧跳过 3 字节帧头。CRC 自身为 2 字节大端。
2. **帧头扫描与长度检查限制**：接收侧会累计数据、滑动扫描帧头并按 Len 截取，但未完整校验各帧最小长度；`16 02 02` 还被两个通道复用，不能仅按帧头判断长度字段宽度。
3. **帧中的多字节整数为大端**；新增字段时用 `SEBinaryConverter` 并注意 `.Reverse()`。ASCII 学号的十六进制还原是例外，见 §5.5。
4. **62 vs 64 字节数据帧**：源码支持两种长度分支，序号宽度（2/4 字节）与记录体偏移（8/10）不同；这不能证明具体固件版本的支持情况。新增报文格式需核对 `DataResponse` / `HeadResponse`；`DataResponse` 对其它长度不会复制记录体，也没有明确拒绝未知格式。
5. **学号还原逻辑**（`RevertNumber`）：8 位且含 A-F、各字符均可按十六进制解析的学号，会将依次解析的 4 字节按小端转回数字，改学号编码规则时注意兼容。
6. **成功判据按通道和方法区分**：多数普通命令要求 `CMDState == 0xB3`，但读取主机号、读取参数、`GotoMainForm` 有例外（§4）；学生下载使用 `CommandRet`（§6）。尤其不能把停止重发等同于业务成功（§2.3、§6.3）。
7. **并发上限 4 的适用范围**：事后采集与学生下载各有独立的工作/等待队列；实时采集绕过采集队列。批量操作大量主机时 UI 需显示排队状态。
8. **学生下发调用顺序**：UI 在下发前调用 `PreDownloadStudent (0xA4)`，`StudentDownloader.Close()` 内调用 `CompleteDownload (0x11)`。这是客户端流程；遗漏结束通知是否导致名单不固化，需要固件协议或真机确认，源码不能证明。
9. **调试日志**：各类的 `Log = true` 时通过 `FileLog` 输出收发报文十六进制（「执行命令{主机号}」「数据采集{主机号}」「下载学生{主机号}」），主机管理 UI 上有日志开关（`chkLog`）。日志依赖各实例的 Log 值，并不自动涵盖全部报文，例如采集 `Close()` 内新建的 `WifiHost` 未复制 Log。
10. 本协议代码为从 `lib/Device.dll` 反编译恢复的源码（文件头标注 "Recovered from lib/Device.dll"），修改前建议先用真机回归验证。
11. **短头帧接收风险**：`HostWifiReader.GetHeadPacket()` 要求累计接收缓冲至少 62 字节才扫描头帧。因此单独到达的 18 / 24 字节头帧不会立即解析；下一轮发送又会清空缓冲，可能影响无数据头帧的完成判断。这是当前实现限制，不是协议要求头帧必须达到 62 字节。
12. **新版序号接收与请求宽度不同**：接收可解析 4 字节序号，但轮询请求仍只携带 2 字节（§5.2）；不能据此认为已完整支持 32 位序号续传。
13. **异常命令应答可能使接收循环卡住**：`WifiHost.Socket_OnDataArrivedEvent` 在命令应答 CRC 不合法或 CMD 不匹配时，既不取下一包也不退出 while，并持有 `_DataLocker`。因此“坏包会被安全丢弃并重试”不符合当前实现。
14. **未知字段与固件语义**：头帧未读取区、成绩帧偏移 5、命令应答偏移 9-10，以及下载数据区的固定 01 / 00，源码不足以确定语义。固件的重复命令去重、范围边界、存储完成时机、不同固件版本支持范围均待设备侧证据确认。
